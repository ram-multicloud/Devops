# GitHub Actions: Outputs and Matrix Strategy

## Outputs

Outputs let one job or step pass data to another. They are the mechanism for communication across the otherwise isolated execution contexts of steps and jobs.

### Step Outputs

A step writes a key-value pair to the special `GITHUB_OUTPUT` environment file. Other steps in the **same job** can read it via `steps.<step_id>.outputs.<name>`.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Set version
        id: version_step
        run: echo "version=1.2.3" >> "$GITHUB_OUTPUT"

      - name: Use version
        run: echo "Building version ${{ steps.version_step.outputs.version }}"
```

### Job Outputs

To pass a value **between jobs**, the producing job must declare it under `outputs:`, referencing the step output. The consuming job accesses it via `needs.<job_id>.outputs.<name>` and must declare `needs:`.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.version_step.outputs.version }}
    steps:
      - name: Set version
        id: version_step
        run: echo "version=1.2.3" >> "$GITHUB_OUTPUT"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Deploy
        run: echo "Deploying version ${{ needs.build.outputs.version }}"
```

Key points:
- Outputs are always strings.
- A step output only exists if the step ran (skipped steps produce no output).
- Job outputs must be explicitly re-declared at the job level; they are not automatically visible to downstream jobs.

## 2. Matrix Strategy

A matrix runs the same job multiple times with different variable combinations — one job execution per combination — instead of duplicating job definitions.

### 2.1 Basic Matrix

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [16, 18, 20]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm test
```

This creates 3 parallel jobs, one per Node version, each with `matrix.node-version` set accordingly.

### 2.2 Multiple Dimensions

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest]
        node-version: [16, 18]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm test
```

This produces the full cross-product: 2 OSes × 2 Node versions = 4 jobs.

### 2.3 `include` and `exclude`

`exclude` removes specific combinations; `include` adds extra combinations or extra variables tied to a specific combination.

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    node-version: [16, 18, 20]
    exclude:
      - os: windows-latest
        node-version: 16
    include:
      - os: ubuntu-latest
        node-version: 20
        experimental: true
```

### 2.4 `fail-fast` and `max-parallel`

```yaml
strategy:
  fail-fast: false
  max-parallel: 2
  matrix:
    node-version: [16, 18, 20]
```

- `fail-fast: true` (default) cancels all remaining matrix jobs if one fails.
- `max-parallel` caps how many matrix jobs run concurrently.

## 3. Dynamic Environment Variables

A step can set an environment variable at runtime for use by **subsequent steps in the same job**, by writing to the `GITHUB_ENV` file. Unlike outputs, these become plain environment variables (`$VAR` or `env.VAR`), not `steps.*.outputs.*`.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Set dynamic env var
        run: echo "BUILD_ID=build-$(date +%s)" >> "$GITHUB_ENV"

      - name: Use env var
        run: echo "Running build ${{ env.BUILD_ID }}"

      - name: Also available as shell var
        run: echo "Running build $BUILD_ID"
```

Key points:
- `GITHUB_ENV` variables persist for the rest of the job, across all later steps.
- They do **not** carry over to other jobs — use job outputs for that.
- Multi-line values need a delimiter syntax:

```yaml
- run: |
    echo "REPORT<<EOF" >> "$GITHUB_ENV"
    echo "line one" >> "$GITHUB_ENV"
    echo "line two" >> "$GITHUB_ENV"
    echo "EOF" >> "$GITHUB_ENV"
```

## 4. GitHub Step Summary

Each step can write Markdown to `GITHUB_STEP_SUMMARY`, which is rendered in the workflow run's summary page — useful for test results, reports, or deployment details without digging through logs.

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Run tests
        run: npm test

      - name: Write summary
        run: |
          echo "## Test Results" >> "$GITHUB_STEP_SUMMARY"
          echo "- Passed: 42" >> "$GITHUB_STEP_SUMMARY"
          echo "- Failed: 0" >> "$GITHUB_STEP_SUMMARY"
```

Combined with a matrix, each matrix job can append its own section to the summary:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [16, 18, 20]
    steps:
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm test
      - name: Write summary
        run: |
          echo "### Node ${{ matrix.node-version }}" >> "$GITHUB_STEP_SUMMARY"
          echo "Tests passed" >> "$GITHUB_STEP_SUMMARY"
```

Key points:
- Content is standard Markdown (tables, headers, lists all render).
- Each job/step appends to the same summary file for that job; content from parallel matrix jobs appears as separate summary sections, not merged into one.
- The file is capped at 1 MiB per job.

## 5. Combining Outputs with a Matrix

A matrix job cannot expose a single scalar job output directly, since it runs multiple times. To collect a result from every matrix combination, write per-job outputs and aggregate them in a downstream job (e.g. via artifacts, or by fanning results into a JSON structure read by a summary job).

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: [16, 18, 20]
    outputs:
      result-16: ${{ steps.run_tests.outputs.result }}
    steps:
      - id: run_tests
        run: echo "result=passed" >> "$GITHUB_OUTPUT"
```

In practice, teams use artifacts or a dedicated aggregation step rather than naming one output per matrix value, since job outputs don't merge automatically across matrix instances.
