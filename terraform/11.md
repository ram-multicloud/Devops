# Terraform Provisioners

### What they are
Provisioners let Terraform run **scripts or commands** on a local machine or a remote resource, either right after a resource is created (`creation-time`) or right before it's destroyed (`destroy-time`). They exist for edge cases where Terraform's declarative model can't do the job — e.g., bootstrapping a VM, copying a config file, or triggering a config-management tool.

> ⚠️ **HashiCorp's official guidance**: Provisioners are a **last resort**. Prefer native provider features (e.g., `user_data` for AWS EC2), cloud-init, or dedicated config management tools (Ansible, Chef, Puppet) whenever possible. Terraform cannot track changes made by provisioners, so they break the "plan reflects reality" guarantee.

### Types of Provisioners

| Provisioner | Purpose |
|---|---|
| `local-exec` | Runs a command on the machine **running Terraform** (not the resource) |
| `remote-exec` | Runs a command **on the remote resource** (via SSH/WinRM) |
| `file` | Copies files/directories **from local machine to the remote resource** |

### 1.1 `local-exec` Example

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"

  provisioner "local-exec" {
    command = "echo 'Instance ${self.id} created with IP ${self.public_ip}' >> instance_log.txt"
  }
}
```

- `self.id` and `self.public_ip` refer to attributes of the resource the provisioner is attached to.
- This runs **on your laptop/CI runner**, not on the EC2 instance.

### 1.2 `remote-exec` Example

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"
  key_name      = "my-keypair"

  connection {
    type        = "ssh"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
    host        = self.public_ip
  }

  provisioner "remote-exec" {
    inline = [
      "sudo apt-get update -y",
      "sudo apt-get install -y nginx",
      "sudo systemctl start nginx"
    ]
  }
}
```

- Requires a `connection` block (SSH or WinRM) so Terraform knows how to reach the instance.
- `inline` runs a list of commands in order.

### 1.3 `file` Provisioner Example

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"
  key_name      = "my-keypair"

  connection {
    type        = "ssh"
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
    host        = self.public_ip
  }

  provisioner "file" {
    source      = "app_config/nginx.conf"
    destination = "/tmp/nginx.conf"
  }
}
```

- Copies a local file to a path on the remote resource. Often paired with `remote-exec` to then move it to a system path (e.g., `/etc/nginx/`).

### 1.4 `when = destroy` (Destroy-Time Provisioner)

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"

  provisioner "local-exec" {
    when    = destroy
    command = "echo 'Instance ${self.id} is being destroyed' >> destroy_log.txt"
  }
}
```

- Runs **before** the resource is destroyed. Useful for deregistering nodes from a load balancer, notifying a system, etc.
- Destroy-time provisioners **cannot use most attributes** other than `self`, since the resource is about to be gone.

### 1.5 Failure Behavior

```hcl
provisioner "local-exec" {
  command    = "some-script-that-might-fail.sh"
  on_failure = continue   # default is "fail"
}
```

- `on_failure = fail` (default): Terraform stops and marks the resource as **tainted**.
- `on_failure = continue`: Terraform ignores the error and proceeds.

## 2. Terraform Local Variables (`locals`)

### What they are
`locals` let you assign a name to an expression so you can **reuse it** throughout a module without repeating logic. Unlike input variables (`variable`), locals aren't set by the caller — they're computed internally, often by combining variables, data sources, or other locals.

### Basic Syntax

```hcl
locals {
  environment  = "production"
  project_name = "myapp"
  common_tags = {
    Environment = local.environment
    Project     = local.project_name
    ManagedBy   = "Terraform"
  }
}
```

Reference a local anywhere in the module with `local.<name>` (singular "local", note the difference from the `locals` block name).

### Example: Reducing Repetition

```hcl
variable "project" {
  default = "orders-service"
}

variable "env" {
  default = "dev"
}

locals {
  name_prefix = "${var.project}-${var.env}"
}

resource "aws_s3_bucket" "data" {
  bucket = "${local.name_prefix}-data"
}

resource "aws_iam_role" "app_role" {
  name = "${local.name_prefix}-role"
}
```

Both resources use the same computed prefix — change the logic once in `locals`, and it propagates everywhere.

### Example: Computed Logic / Conditionals

```hcl
variable "instance_count" {
  default = 3
}

locals {
  is_production   = var.env == "prod"
  instance_type   = local.is_production ? "t3.large" : "t3.micro"
  final_count     = local.is_production ? var.instance_count * 2 : var.instance_count
}

resource "aws_instance" "app" {
  count         = local.final_count
  instance_type = local.instance_type
  ami           = "ami-0c94855ba95c71c99"
}
```

### Example: Merging Tags (a very common real-world pattern)

```hcl
locals {
  default_tags = {
    ManagedBy = "Terraform"
    Team      = "platform"
  }

  merged_tags = merge(local.default_tags, var.extra_tags)
}

resource "aws_instance" "app" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"
  tags          = local.merged_tags
}
```

### Key Points
- `locals` are **not** settable from the CLI or `.tfvars` — they're internal to the module.
- They help avoid "magic strings" repeated across many resources.
- Good for derived/computed values: naming conventions, conditional logic, merged maps, formatted strings.
- Scope is per-module — locals in a child module aren't visible in the parent (and vice versa) unless explicitly passed as outputs/inputs.

## 3. `null_resource`

### What it is
`null_resource` is a resource that does **nothing on its own** — it has no real infrastructure behind it. It exists purely as an **attachment point for provisioners** or to control execution order/triggers, especially when there's no "real" resource that naturally fits the job.

> Note: In newer Terraform (0.15.5+/1.x with the null provider), `null_resource` still works, but for many use cases the `terraform_data` resource (built into Terraform core since 1.4) is the modern replacement. `null_resource` remains extremely common in real-world code and interviews, so it's still important to know.

### Requires the `null` provider

```hcl
terraform {
  required_providers {
    null = {
      source  = "hashicorp/null"
      version = "~> 3.0"
    }
  }
}
```

### Basic Example

```hcl
resource "null_resource" "example" {
  provisioner "local-exec" {
    command = "echo 'This runs because null_resource has no real infra to manage'"
  }
}
```

### Example: `triggers` to Control Re-execution

By default, `null_resource` only runs its provisioner **once**, at creation. Terraform doesn't know when to re-run it unless you tell it to via `triggers` — a map of values that, when changed, force the resource to be recreated (and its provisioner re-run).

```hcl
resource "null_resource" "run_migration" {
  triggers = {
    script_hash = filesha256("scripts/migrate.sh")
  }

  provisioner "local-exec" {
    command = "bash scripts/migrate.sh"
  }
}
```

- Every time `migrate.sh` changes, its hash changes, `triggers` changes, Terraform destroys/recreates the `null_resource`, and the script re-runs.
- Without `triggers`, editing the script would NOT cause Terraform to re-run it.

### Example: Ordering / Dependency Chaining

`null_resource` is often used to force ordering between resources that don't have a natural dependency, using `depends_on`.

```hcl
resource "aws_instance" "db" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t3.medium"
}

resource "aws_instance" "app" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t3.medium"
}

resource "null_resource" "wait_for_db" {
  depends_on = [aws_instance.db]

  provisioner "local-exec" {
    command = "echo 'DB is up, now configuring app server' "
  }
}

resource "null_resource" "configure_app" {
  depends_on = [null_resource.wait_for_db, aws_instance.app]

  connection {
    type        = "ssh"
    host        = aws_instance.app.public_ip
    user        = "ubuntu"
    private_key = file("~/.ssh/id_rsa")
  }

  provisioner "remote-exec" {
    inline = ["echo 'App configured after DB was confirmed ready'"]
  }
}
```

### Example: Running a Provisioner Against an Existing Resource (using `self` doesn't exist here, so reference resource directly)

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"
}

resource "null_resource" "notify_slack" {
  triggers = {
    instance_id = aws_instance.web.id
  }

  provisioner "local-exec" {
    command = "curl -X POST -H 'Content-type: application/json' --data '{\"text\":\"New instance ${aws_instance.web.id} launched\"}' https://hooks.slack.com/services/XXX"
  }
}
```

### When to Use `null_resource`
- Running a script that depends on multiple resources but isn't tied to any single one.
- Triggering configuration management (Ansible playbook run, etc.) after infra is up.
- Forcing a re-run of a provisioner when specific inputs change (via `triggers`).
- Sequencing operations where Terraform's implicit dependency graph doesn't capture the real-world order you need.

## 4. `terraform import`

### What it is
`terraform import` brings **existing infrastructure** (created manually, via another tool, or by a script) **under Terraform's management**, by mapping a real-world resource to a resource block in your `.tf` code and recording it in the **state file**.

> Important: `import` only updates the **state**. It does **not** generate `.tf` configuration for you (in Terraform < 1.5). You must write the matching resource block yourself, or the next `terraform plan` will show a diff trying to "fix" your resource to match an empty/default config — potentially destroying or altering it.

### Classic Workflow (Terraform < 1.5, or the traditional CLI approach)

**Step 1: Write a resource block (can be mostly empty at first)**

```hcl
resource "aws_instance" "web" {
  # will be filled in after import
}
```

**Step 2: Run the import command**

```bash
terraform import aws_instance.web i-0abcd1234efgh5678
```

- `aws_instance.web` — the resource address in your `.tf` file.
- `i-0abcd1234efgh5678` — the real-world resource ID (varies per provider/resource type — check provider docs for the exact ID format).

**Step 3: Inspect the imported state**

```bash
terraform state show aws_instance.web
```

This prints all the attributes Terraform now knows about the resource.

**Step 4: Copy the relevant attributes into your `.tf` file**

```hcl
resource "aws_instance" "web" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"
  key_name      = "my-keypair"
  subnet_id     = "subnet-0123456789abcdef0"
  tags = {
    Name = "web-server"
  }
}
```

**Step 5: Confirm no diff**

```bash
terraform plan
```

If configured correctly, `plan` should show **no changes**. If it shows changes, adjust your `.tf` code to match reality until the plan is clean.

### Example: Importing an S3 Bucket

```hcl
resource "aws_s3_bucket" "assets" {
  # populate after import
}
```

```bash
terraform import aws_s3_bucket.assets my-existing-bucket-name
```

### Example: Importing a Resource Inside a Module

```bash
terraform import module.network.aws_vpc.main vpc-0a1b2c3d4e5f6g7h8
```

### Modern Approach: `import` Block (Terraform 1.5+)

Newer Terraform lets you declare imports **as code**, which is safer and repeatable (and works with `terraform plan`/`apply` instead of a separate imperative command):

```hcl
import {
  to = aws_instance.web
  id = "i-0abcd1234efgh5678"
}

resource "aws_instance" "web" {
  ami           = "ami-0c94855ba95c71c99"
  instance_type = "t2.micro"
}
```

Then:

```bash
terraform plan     # shows the import + any config drift
terraform apply    # performs the import
```

Terraform 1.5+ can also **generate configuration automatically**:

```bash
terraform plan -generate-config-out=generated.tf
```

This writes a best-effort `.tf` file for the imported resource, which you then review/clean up — much faster than manually copying attributes from `terraform state show`.

### Key Points on Import
- Import is **1 resource at a time** with the classic CLI command (though `import` blocks can be batched/looped in 1.5+).
- Always run `terraform plan` after importing to verify your config matches reality exactly.
- Get the correct **resource ID format** from the provider's documentation — it differs per resource type (e.g., ARN for some AWS resources, just a name for others).
- Does not import child/dependent resources automatically (e.g., importing a VPC doesn't import its subnets — each needs its own import).

## Quick Comparison Table

| Feature | Purpose | Runs Where | State Impact |
|---|---|---|---|
| **Provisioner** | Run scripts at create/destroy time | Local machine or remote resource | None directly (side-effect only) |

| **null_resource** | Anchor for provisioners / control ordering | N/A itself; provisioners inside run local/remote | Creates a placeholder resource in state |
