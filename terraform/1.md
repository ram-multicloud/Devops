## Why do we even need Terraform? (The Story)

Imagine you're a cloud engineer. Your manager gives you a task:

> "Set up a **test environment** for a customer: a network, one Ubuntu server, and a MySQL database — on AWS."

You do it. Then a teammate says the customer actually wants a bigger **production
environment**: a network, **two** Ubuntu servers, a load balancer, and a MySQL database.

Now think about how you'd actually build this. There are three ways:

| Approach | What it looks like | Problem with it |
|---|---|---|
| **Manual clicking** | Create everything by hand in the AWS Console | Slow, easy to forget a step, hard to repeat for a second environment |
| **Scripts (CLI/SDK)** | A bash script or Python program that calls AWS commands one by one | You must write every single step yourself (create VPC → create subnet → create gateway → ...). If something already exists, the script may fail or duplicate it |
| **Infrastructure as Code (Terraform)** | You just describe *what you want the end result to look like* | Terraform figures out the steps and only makes the changes that are actually needed |

**The key idea:** Scripts are *imperative* — you say "do this, then this, then this."
Terraform is *declarative* — you say "this is what I want the final setup to look like,"
and Terraform works out how to get there.

### What the "hard way" looks like

A bash script using the AWS CLI has to manually create every piece, one command at a time —
VPC, subnet, internet gateway, route table, security groups, EC2 instance, and finally the
database:

```bash
#!/bin/bash
set -e

REGION="ap-south-1"
VPC_CIDR="10.0.0.0/16"

VPC_ID=$(aws ec2 create-vpc --cidr-block $VPC_CIDR --region $REGION \
  --query 'Vpc.VpcId' --output text)

SUBNET_ID=$(aws ec2 create-subnet --vpc-id $VPC_ID --cidr-block 10.0.1.0/24 \
  --region $REGION --query 'Subnet.SubnetId' --output text)

# ...and many more steps for the gateway, routes, security groups,
#    EC2 instance, and RDS database
```

The same thing can be written in Python with `boto3` instead of bash — same idea, same
number of manual steps, just a different language.

### What the "Terraform way" looks like

Instead of listing steps, you describe the **end result**:

```hcl
provider "aws" {
  region = var.region
}

resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
  tags = { Name = "main-vpc" }
}

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"
  map_public_ip_on_launch = true
  tags = { Name = "public-subnet" }
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = "t2.micro"
  subnet_id              = aws_subnet.public.id
  key_name               = var.key_name
  tags = { Name = "ubuntu-ec2" }
}

resource "aws_db_instance" "mysql" {
  identifier          = "my-mysql-db"
  engine              = "mysql"
  instance_class      = "db.t3.micro"
  allocated_storage   = 20
  username            = "admin"
  password            = var.db_password
  skip_final_snapshot = true
}
```

That's it. Terraform reads this file, checks what already exists, and creates only what's
missing. If you run it again and nothing changed, it does nothing — that's the power of
"describing the desired state" instead of writing steps.

## 2. The building blocks of a Terraform file

Every Terraform file is built from five simple ideas:

| Term | Plain-English meaning |
|---|---|
| **Provider** | The "translator" for a specific cloud — AWS, Azure, GCP, etc. It's what lets Terraform actually talk to that cloud's API. |
| **Resource** | One piece of infrastructure you want to create — a server, a bucket, a database, a network. |
| **Data Source** | A way to *look up* something that already exists (instead of creating it) — e.g. "find me the latest Ubuntu image." |
| **Argument** | The **inputs** you give a resource — like the size of a server, or the name of a bucket. |
| **Attribute** | The **outputs** a resource gives you back after it's created — like its auto-generated ID. |

Think of a `resource` block like a function call: the arguments go in, and once it runs, you
get attributes back out.

You can browse all the available providers on the
[Terraform Registry](https://registry.terraform.io/browse/providers).

## 3. How to actually build a Terraform template — step by step

1. **Create a folder** for your project.
2. **Create a file ending in `.tf`** — this is where you write your configuration in HCL
   (HashiCorp Configuration Language).
3. **Write the provider block** — this tells Terraform which cloud you're using:

   ```hcl
   provider "aws" {
     region = "ap-south-1"
   }
   ```

4. **Run `terraform init`** — this downloads the provider plugin (the AWS "translator")
   so Terraform can actually talk to AWS.
5. **Write a resource block** — this is the thing you actually want to create. For example,
   an S3 bucket:

   ```hcl
   resource "aws_s3_bucket" "first" {
     bucket = "qt-apr-1-test-from-tf"
   }
   ```

   - `aws_s3_bucket` is the resource **type**.
   - `"first"` is just a local nickname you're giving this particular bucket, so you can
     refer to it elsewhere in your code.
   - `bucket = "..."` is an **argument** — an input.

6. **Run `terraform apply`** — Terraform creates the resource for real.
7. **Run `terraform destroy`** — when you're done, this tears everything back down.

### Finding the right syntax
You don't need to memorize every resource. Just look it up:
- Search "terraform aws s3 bucket" (or whichever provider + resource you need)
- Or check the [AWS provider docs](https://registry.terraform.io/providers/hashicorp/aws/latest/docs)
- Or the general [resource block reference](https://developer.hashicorp.com/terraform/language/block/resource)

## 4. The general workflow for any new piece of infrastructure

Whenever you need to create something new with Terraform, follow this repeatable process:

1. **Figure out the manual steps first** — e.g. "How would I create this by clicking around
   in the AWS Console?" Understanding the manual process helps you understand what
   Terraform needs to do.
2. **Pick the right provider** (AWS, Azure, GCP...).
3. **Write the resource block(s)** with the correct arguments.
4. **Run the Terraform commands**:
   ```bash
   terraform init
   terraform apply
   terraform destroy
   ```

---

## 5. Quick recap

- **Manual clicking** and **CLI/SDK scripts** are both "imperative" — you control every step.
- **Terraform** is "declarative" — you describe the end goal, and Terraform figures out the
  steps, while also keeping track of what it already created.
- A Terraform file is made of **providers**, **resources**, **data sources**, **arguments**
  (inputs), and **attributes** (outputs).
- The basic loop you'll use constantly is: **write HCL → `terraform init` → `terraform apply`
  → (when done) `terraform destroy`.**
