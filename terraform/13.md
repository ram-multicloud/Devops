# Terraform Workspaces

## What is a Terraform Workspace?

A **workspace** lets you reuse the *same* Terraform configuration for multiple environments (like `dev`, `staging`, `prod`) while keeping each environment's **state completely separate**.

```
Same Terraform Code
        |
   +----+----+
   |         |
 dev       prod
workspace  workspace
   |         |
dev state  prod state
```

The code doesn't change — only the state (i.e., what Terraform thinks exists) is different per workspace. So you can apply the same `main.tf` to `dev` and get 1 small instance, then apply it to `prod` and get 2 bigger instances — without maintaining two separate codebases.

> **Key thing to remember:** a workspace is *not* a Git branch. Git branches version your code; Terraform workspaces version your *state*. They're independent — you could be on Git branch `main` while sitting in Terraform workspace `dev` or `prod`.

## Setting It Up (Step by Step)

### 1. Create a project
```bash
mkdir terraform-workspace-example
cd terraform-workspace-example
```

### 2. Write a simple `main.tf`
References `terraform.workspace` — a built-in variable holding the current workspace name:
```hcl
resource "local_file" "example" {
  filename = "${path.module}/${terraform.workspace}.txt"
  content  = "Hello from Terraform!\nWorkspace: ${terraform.workspace}"
}
```

### 3. Initialize
```bash
terraform init
```

### 4. Check your current workspace
```bash
terraform workspace show
```
You'll start on `default`.

### 5. Create and use a `dev` workspace
```bash
terraform workspace new dev
terraform apply
```
This creates `dev.txt` — tracked in its own state.

### 6. Create and use a `prod` workspace
```bash
terraform workspace new prod
terraform apply
```
This creates `prod.txt` — tracked in a *separate* state from `dev`.

### 7. Switch between them anytime
```bash
terraform workspace select dev
terraform workspace select prod
```

## Making Environments Actually Differ

Just switching workspaces doesn't change resource sizes by itself — you drive that with a lookup map keyed on `terraform.workspace`:

```hcl
locals {
  environment_config = {
    dev  = { instance_type = "t2.micro",  instance_count = 1 }
    prod = { instance_type = "t3.medium", instance_count = 2 }
  }
  config = local.environment_config[terraform.workspace]
}

resource "aws_instance" "app" {
  count         = local.config.instance_count
  ami           = "ami-12345678"
  instance_type = local.config.instance_type
  tags          = { Environment = terraform.workspace }
}
```

Now `dev` deploys 1 small instance, `prod` deploys 2 medium instances — same code, different outcome, driven by which workspace is active.

## Cheat Sheet

| Command | What it does |
|---|---|
| `terraform workspace list` | Show all workspaces (`*` = active one) |
| `terraform workspace show` | Show current workspace |
| `terraform workspace new dev` | Create + switch to a new workspace |
| `terraform workspace select dev` | Switch to an existing workspace |
| `terraform workspace delete dev` | Delete a workspace (must switch off it first) |

## When *Not* to Use Workspaces

Workspaces are great for lightweight, structurally-similar environments. But watch out:

- It's easy to accidentally run `apply` in the wrong workspace — always run `terraform workspace show` before a `prod` apply.
- For large or meaningfully different production environments, many teams instead use **separate directories/configs** (`dev/`, `prod/`, each with their own `.tf` files and state backend) for stronger isolation, rather than relying on workspaces alone.

**Bottom line:** one config, many workspaces, each with its own isolated state — great for keeping things DRY across similar environments, but not a substitute for real isolation when environments diverge a lot.
