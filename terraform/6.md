# Terraform State Management

## What is the State File?
Terraform stores information about your managed infrastructure and configuration in a state file (by default, `terraform.tfstate` in your local directory). 

**Why does Terraform need state?**
1.  **Mapping:** It maps the real-world resources (e.g., an AWS EC2 instance ID) to your code's logical resources (`aws_instance.web`).
2.  **Performance:** It caches resource attributes, so Terraform doesn't have to query the cloud provider API for every single detail during a `plan`.
3.  **Tracking Deletions:** If you remove a resource block from your `.tf` file, Terraform looks at the state to know it must issue a "delete" API call for that specific resource.

## Remote State
By default, state is stored locally. This is dangerous for teams:
*   What if a developer's laptop dies? The state is lost.
*   How do two developers avoid changing the infrastructure at the exact same time (race conditions)?

**Solution: Remote Backends**
You configure Terraform to store the state file in a remote, shared location (like an AWS S3 bucket).

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket-123"
    key            = "global/s3/terraform.tfstate"
    region         = "us-east-1"
    dynamodb_table = "terraform-locks" 
  }
}
```

## State Locking
Notice the `dynamodb_table` in the S3 backend config. When multiple users run Terraform, you need **State Locking**. When User A runs `terraform apply`, Terraform writes a lock to DynamoDB. If User B tries to run `apply` at the same time, Terraform will see the lock and reject User B's run, preventing state corruption.
