# Azure Pipeline, Secrets, and Terraform Authentication — Step by Step

This guide covers three things in order:
1. Creating an Azure DevOps Pipeline
2. Setting up environment variables and secrets
3. Authenticating Terraform to your Azure account

---

## Part 1: Create an Azure Pipeline

### Step 1 — Create an Azure DevOps Organization and Project
1. Go to https://dev.azure.com
2. Sign in with your Microsoft account.
3. Click **New organization** (skip if you already have one).
4. Inside the organization, click **New Project**.
5. Give it a name, set visibility (private/public), click **Create**.

### Step 2 — Connect Your Repository
1. In the project, go to **Repos**.
2. Either import an existing repo (GitHub/Azure Repos/other Git URL) or push your Terraform code into the default repo.

### Step 3 — Create the Pipeline
1. Go to **Pipelines** → **Create Pipeline**.
2. Choose where your code lives: **Azure Repos Git**, **GitHub**, etc.
3. Select your repository.
4. Choose **Starter pipeline** (or "Existing Azure Pipelines YAML file" if you already have one).
5. Azure DevOps generates a default `azure-pipelines.yml` in your repo root.

### Step 4 — Basic Pipeline YAML Structure
```yaml
trigger:
  branches:
    include:
      - main

pool:
  vmImage: 'ubuntu-latest'

steps:
  - script: echo "Hello, pipeline is running"
    displayName: 'Test Step'
```

### Step 5 — Save and Run
1. Click **Save and run**.
2. Commit the YAML file directly to the branch (or create a PR).
3. The pipeline triggers automatically and you can watch live logs under **Pipelines** → **Runs**.

## How to Write a Pipeline (YAML Explained)

An Azure Pipeline is just a YAML file (`azure-pipelines.yml`) in the repo root. It tells Azure DevOps: **when to run**, **where to run**, and **what to do**.

### The 4 Core Blocks

**1. `trigger` — when should this pipeline run?**
```yaml
trigger:
  branches:
    include:
      - main
      - develop
```
Every push to `main` or `develop` fires the pipeline automatically.

**2. `pool` — where should it run?**
```yaml
pool:
  vmImage: 'ubuntu-latest'
```
This is the virtual machine (agent) that executes your commands. Options: `ubuntu-latest`, `windows-latest`, `macOS-latest`.

**3. `variables` — reusable values**
```yaml
variables:
  environment: 'dev'
  terraformVersion: '1.7.0'
```

**4. `steps` — the actual work, run in order**
```yaml
steps:
  - script: echo "Step 1 running"
    displayName: 'Say hello'

  - script: terraform init
    displayName: 'Terraform Init'
```
Each `- script:` is one command (or block of commands). `displayName` is a friendly label shown in the pipeline logs.

### Putting It Together — Minimal Full Example
```yaml
trigger:
  branches:
    include:
      - main

pool:
  vmImage: 'ubuntu-latest'

variables:
  terraformVersion: '1.7.0'

steps:
  - script: echo "Pipeline started"
    displayName: 'Start'

  - script: terraform version
    displayName: 'Check Terraform Version'

  - script: terraform init
    displayName: 'Terraform Init'

  - script: terraform plan
    displayName: 'Terraform Plan'
```

### Scaling Up: Jobs and Stages

Once a pipeline grows, organize `steps` into `jobs`, and `jobs` into `stages`:

```yaml
stages:
  - stage: Build
    jobs:
      - job: Terraform_Init
        pool:
          vmImage: 'ubuntu-latest'
        steps:
          - script: terraform init
            displayName: 'Init'

  - stage: Deploy
    jobs:
      - job: Terraform_Apply
        pool:
          vmImage: 'ubuntu-latest'
        steps:
          - script: terraform apply -auto-approve
            displayName: 'Apply'
```

**Mental model:**
- **Stage** = a phase (Build, Test, Deploy)
- **Job** = a set of steps that run on one agent
- **Step** = one command

**Beginner rule:** Start flat (just `steps:`), get it working, then refactor into `stages`/`jobs` once you need separation (e.g., different approval gates for Build vs Deploy).

## Part 2: Environment Variables and Secrets

There are three common ways to store variables/secrets in Azure Pipelines.

### Option A — Pipeline Variables (UI)
1. Open your pipeline → **Edit** → **Variables** (top right).
2. Click **New variable**.
3. Enter name/value.
4. Check **Keep this value secret** for sensitive values (passwords, keys). Azure DevOps masks it in logs.
5. Reference it in YAML:
```yaml
steps:
  - script: echo "Value is $(MY_VARIABLE)"
```
Secret variables must be mapped explicitly into an environment variable when used as `$(VAR)` inside a script:
```yaml
steps:
  - script: echo $MY_SECRET
    env:
      MY_SECRET: $(mySecretVariable)
```

### Option B — Variable Groups (shared across pipelines)
1. Go to **Pipelines** → **Library**.
2. Click **+ Variable group**.
3. Name the group (e.g., `terraform-azure-creds`).
4. Add variables, mark sensitive ones as **secret** (lock icon).
5. Optionally link to **Azure Key Vault** (toggle "Link secrets from an Azure key vault as variables") to pull secrets directly from Key Vault instead of storing them in Azure DevOps.
6. Save.
7. Reference the group in your pipeline YAML:
```yaml
variables:
  - group: terraform-azure-creds

steps:
  - script: echo "Client ID is $(ARM_CLIENT_ID)"
```

### Option C — Azure Key Vault (recommended for production)
1. Create a Key Vault in Azure Portal (if not already present).
2. Add your secrets (e.g., service principal client secret) into the Key Vault.
3. In Azure DevOps **Library**, create a variable group linked to that Key Vault (as in Option B, step 5).
4. Grant the Azure DevOps service connection **Get/List** permissions on the Key Vault's access policies.
5. Pipeline pulls the latest secret value at run time — no secret is stored inside Azure DevOps itself.

## Part 3: Authenticate Azure Account for Terraform

Terraform needs credentials to talk to the Azure Resource Manager (ARM) API. The standard approach is a **Service Principal**.

### Step 1 — Create a Service Principal
Run this from Azure CLI (or Azure Cloud Shell):
```bash
az login

az account set --subscription "<SUBSCRIPTION_ID>"

az ad sp create-for-rbac --name "terraform-sp" \
  --role="Contributor" \
  --scopes="/subscriptions/<SUBSCRIPTION_ID>"
```

This returns:
```json
{
  "appId": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
  "displayName": "terraform-sp",
  "password": "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "tenant": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
}
```

Map these to Terraform's expected environment variables:

| Terraform Variable | Value from Output |
|---|---|
| `ARM_CLIENT_ID` | `appId` |
| `ARM_CLIENT_SECRET` | `password` |
| `ARM_TENANT_ID` | `tenant` |
| `ARM_SUBSCRIPTION_ID` | Your subscription ID |

### Step 2 — Store These as Secrets in Azure DevOps
1. Go to **Pipelines** → **Library** → create/open a variable group (e.g., `terraform-azure-creds`).
2. Add:
   - `ARM_CLIENT_ID` (secret)
   - `ARM_CLIENT_SECRET` (secret)
   - `ARM_TENANT_ID` (secret)
   - `ARM_SUBSCRIPTION_ID` (secret)
3. Save.

### Step 3 — Reference in Pipeline YAML
```yaml
variables:
  - group: terraform-azure-creds

steps:
  - script: |
      terraform init
      terraform plan
      terraform apply -auto-approve
    displayName: 'Terraform Init/Plan/Apply'
    env:
      ARM_CLIENT_ID: $(ARM_CLIENT_ID)
      ARM_CLIENT_SECRET: $(ARM_CLIENT_SECRET)
      ARM_TENANT_ID: $(ARM_TENANT_ID)
      ARM_SUBSCRIPTION_ID: $(ARM_SUBSCRIPTION_ID)
```

Terraform's `azurerm` provider automatically picks up these `ARM_*` environment variables — no need to hardcode credentials in `.tf` files:
```hcl
provider "azurerm" {
  features {}
}
```

### Step 4 (Alternative) — Use Azure DevOps Service Connection + AzureCLI Task
Instead of manually managing a service principal's secret, you can use an Azure DevOps **Service Connection**:
1. Go to **Project Settings** → **Service connections** → **New service connection**.
2. Choose **Azure Resource Manager**.
3. Choose **Service principal (automatic)** — Azure DevOps creates and manages the SP for you.
4. Name it (e.g., `azure-terraform-connection`) and select the target subscription.
5. Use it in the pipeline with the `AzureCLI@2` task:
```yaml
steps:
  - task: AzureCLI@2
    inputs:
      azureSubscription: 'azure-terraform-connection'
      scriptType: 'bash'
      scriptLocation: 'inlineScript'
      inlineScript: |
        terraform init
        terraform plan
        terraform apply -auto-approve
```
This method avoids storing `ARM_CLIENT_SECRET` yourself — Azure DevOps handles the token exchange behind the scenes.

## Quick Reference Summary

| Task | Where |
|---|---|
| Create pipeline | Pipelines → Create Pipeline |
| Store single secret | Pipeline → Edit → Variables |
| Store shared secrets | Pipelines → Library → Variable Group |
| Store secrets securely (prod) | Azure Key Vault → linked Variable Group |
| Authenticate Terraform | Service Principal (`ARM_*` vars) or Service Connection + `AzureCLI@2` task |
