# Docker Multi-Stage Builds

## What it is

A multi-stage build is a single `Dockerfile` that contains **more than one `FROM` instruction**. Each `FROM` starts a new *stage* with its own base image and its own filesystem. Later stages can copy selected files from earlier stages using `COPY --from=<stage>`.

Only the **last stage** becomes the final image. Everything in the earlier stages (compilers, SDKs, source code, build caches, intermediate artifacts) is discarded unless explicitly copied forward.

## The problem it solves

Before multi-stage builds, you had two bad options:

1. **One fat image** — install the SDK/compiler/build tools in the same image that runs the app. The result is huge, slow to pull, and has a large attack surface (compilers and package managers shipped to production).
2. **Builder pattern with two Dockerfiles** — one `Dockerfile.build` to produce the artifact, a shell script to `docker cp` it out, and a second `Dockerfile` to package it. Works, but means multiple files and glue scripts to maintain.

Multi-stage builds give you the small final image without the glue.

## Key syntax

```dockerfile
FROM <base> AS <stage-name>      # name a stage
COPY --from=<stage-name> src dst # copy from a named stage
COPY --from=<index> src dst      # copy by stage number (0-based)
COPY --from=nginx:alpine  ...    # copy directly from an external image
```

Build a specific stage only:

```bash
docker build --target build -t myapp:build .
```

Useful build flags:

```bash
docker build --platform linux/amd64 -t myapp:1.0 .
docker build --build-arg VERSION=1.2.3 -t myapp:1.2.3 .
```

## How the stages are named

| Way to reference | Example | Notes |
|---|---|---|
| By name | `COPY --from=build /app .` | Preferred — readable, order-independent |
| By index | `COPY --from=0 /app .` | Fragile; breaks when stages are reordered |
| External image | `COPY --from=alpine:3.20 /etc/ssl /etc/ssl` | No `FROM` for that stage required |

## Example 1: .NET / nopCommerce

Stage 1 uses the full SDK to build and publish. Stage 2 uses the much smaller ASP.NET runtime image and only receives the published output.

```dockerfile
# Stage 1: build
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish src/Presentation/Nop.Web/Nop.Web.csproj -c Release -o /app/published

# Stage 2: runtime
FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS runtime
WORKDIR /app
COPY --from=build /app/published .
ENV ASPNETCORE_URLS=http://+:5000
ENV ASPNETCORE_ENVIRONMENT=Production
EXPOSE 5000
ENTRYPOINT ["dotnet", "Nop.Web.dll"]
```

The SDK image is roughly 800 MB; the runtime image is roughly 220 MB. The source tree, NuGet cache and compiler never reach the final image.

## Example 2: Download-and-prepare stage

Sometimes the first stage does no compilation at all — it just fetches and unpacks. `wget` and `unzip` stay out of the final image.

```dockerfile
# Stage 1: download and prepare
FROM debian:bookworm-slim AS prep
WORKDIR /src
RUN apt-get update && apt-get install -y wget unzip \
    && wget https://example.com/app_linux_x64.zip \
    && unzip app_linux_x64.zip -d app \
    && mkdir -p app/bin app/logs

# Stage 2: runtime
FROM mcr.microsoft.com/dotnet/aspnet:9.0 AS runtime
WORKDIR /app
COPY --from=prep /src/app .
ENTRYPOINT ["dotnet", "Nop.Web.dll"]
```

## Example 3: Java with Maven

```dockerfile
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
# copy poms first so dependency layer caches independently of source changes
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B clean package -DskipTests

FROM eclipse-temurin:21-jre-alpine AS runtime
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

## Example 4: Node.js — build assets, serve with nginx

```dockerfile
FROM node:22-alpine AS build
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine AS runtime
COPY --from=build /src/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

Node, npm and `node_modules` are all left behind in the build stage.

## Example 5: Go — static binary on scratch

```dockerfile
FROM golang:1.23-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o /out/server ./cmd/server

FROM scratch AS runtime
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/server /server
EXPOSE 8080
ENTRYPOINT ["/server"]
```

Final image is a few megabytes: no shell, no package manager, no OS.

## Example 6: Python with a virtualenv

```dockerfile
FROM python:3.12-slim AS build
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.12-slim AS runtime
COPY --from=build /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
WORKDIR /app
COPY . .
CMD ["python", "app.py"]
```

Build toolchains needed to compile wheels stay in the first stage.

## Example 7: Multiple stages — test, lint, build

Stages can branch; they do not have to be a straight line.

```dockerfile
FROM node:22-alpine AS base
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .

FROM base AS test
RUN npm test

FROM base AS lint
RUN npm run lint

FROM base AS build
RUN npm run build

FROM nginx:alpine AS runtime
COPY --from=build /src/dist /usr/share/nginx/html
```

In CI, run each gate independently:

```bash
docker build --target test .
docker build --target lint .
docker build -t myapp:1.0 .
```

With BuildKit, `test` and `lint` are built in parallel because neither depends on the other.

## Benefits

- **Smaller images** — final image carries runtime dependencies only.
- **Smaller attack surface** — no compilers, package managers, SSH keys or source code shipped.
- **No secret leakage** — a token used in an early stage does not persist into the final image (as long as it is not copied forward).
- **One file, one build** — no external scripts to extract artifacts.
- **Reproducible builds** — the build environment is pinned in the Dockerfile, not on the CI agent.
- **Parallelism** — BuildKit builds independent stages concurrently.

## Layer caching tips

- Copy dependency manifests (`pom.xml`, `package.json`, `requirements.txt`, `go.mod`) and install dependencies **before** copying source. Source changes then do not invalidate the dependency layer.
- Combine `apt-get update` and `apt-get install` in the same `RUN` to avoid stale package indexes from cache.
- Use a `.dockerignore` to keep `.git`, `node_modules`, and local build output out of the build context.

```
.git
node_modules
bin
obj
*.log
```

## Common mistakes

| Mistake | Effect |
|---|---|
| Using `COPY --from=0` instead of a stage name | Breaks silently when stages are reordered |
| Copying the whole build stage forward | Defeats the purpose — image stays large |
| Forgetting CA certificates in a `scratch` image | Outbound HTTPS calls fail |
| No `.dockerignore` | Slow builds, secrets pulled into build context |
| Assuming an unused stage is skipped without BuildKit | Legacy builder builds every stage |

## Verifying the result

```bash
# compare sizes
docker images myapp

# inspect final image layers
docker history myapp:1.0

# confirm build tools are gone
docker run --rm myapp:1.0 which dotnet mvn npm gcc
```
