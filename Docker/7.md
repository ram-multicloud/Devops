# Docker Notes: login, tag, push, ENV, ARG, LABEL

---

## 1. `docker login`

Authenticates your local Docker CLI against a registry (Docker Hub by default, or a private registry).

```
docker login
docker login -u <username>
docker login myregistry.example.com
```

**Flow:**

```
+-----------+        docker login        +------------------+
| Local CLI | -------------------------> |  Registry (Hub /  |
|  (~/.docker/config.json)               |  ECR / GHCR / etc)|
+-----------+ <------------------------- +------------------+
                 auth token stored
```

- Credentials (or a token) get cached in `~/.docker/config.json`.
- Needed before you can `docker push` to a private repo, or `docker pull` from a private one.
- For private registries: `docker login <registry-host>:<port>` (e.g. ECR, GHCR, GitLab registry).
- Logout: `docker logout` or `docker logout myregistry.example.com`.

## 2. `docker tag`

Creates an additional name (alias) for an existing local image. It does **not** copy or duplicate the image — it just adds another reference pointing to the same image ID.

```
docker tag <source_image>[:tag] <target_repo>[:tag]
```

**Example:**

```
docker build -t myapp .
docker tag myapp:latest ramkiran/myapp:1.0
docker tag myapp:latest ramkiran/myapp:latest
```

**Why tag matters before push:** Docker Hub / ECR / GHCR require the image name to be in the form:

```
<registry>/<username-or-org>/<repo>:<tag>
```

If you built as just `myapp`, you must retag it with your Docker Hub username prefix before it can be pushed.

```
+-------------+   docker tag    +----------------------------+
|  myapp:latest| --------------> | ramkiran/myapp:1.0         |
|  (image ID: abc123)            | (same image ID: abc123)    |
+-------------+                  +----------------------------+
```

Check with `docker images` — both tags will show the **same IMAGE ID**.

## 3. `docker push`

Uploads a tagged local image to a registry.

```
docker push ramkiran/myapp:1.0
```

**Full workflow — build → tag → login → push:**

```
+---------+     +-----------+     +------------+     +-------------+
| build   | --> |   tag     | --> |   login    | --> |    push     |
| (local  |     | (rename   |     | (authen-   |     | (upload to  |
| image)  |     | to match  |     | ticate)    |     | registry)   |
|         |     | registry) |     |            |     |             |
+---------+     +-----------+     +------------+     +-------------+
```

Step by step:

```
1. docker build -t myapp .
2. docker tag myapp:latest ramkiran/myapp:1.0
3. docker login
4. docker push ramkiran/myapp:1.0
```

Push all tags of a repo at once: `docker push ramkiran/myapp --all-tags`

Common errors:
| Error | Cause | Fix |
|---|---|---|
| `denied: requested access to the resource is denied` | Not logged in, or wrong namespace | `docker login`, check tag prefix matches your username |
| `repository does not exist` | Repo not created on registry / typo | Create repo on Hub first (Hub auto-creates on push for public repos) |

## 4. Dockerfile `ENV`

Sets an **environment variable** inside the image. Available at both build time (later steps) and run time (inside the running container), and can be overridden at `docker run`.

```dockerfile
FROM ubuntu
ENV APP_ENV=production
ENV PORT=8080
CMD ["sh", "-c", "echo Running in $APP_ENV on port $PORT"]
```

Run and override:
```
docker run myimage
# Running in production on port 8080

docker run -e APP_ENV=staging myimage
# Running in staging on port 8080
```

Check the value inside a running container:
```
docker exec -it <container> printenv APP_ENV
```

## 5. Dockerfile `ARG`

Defines a **build-time only** variable. It does NOT persist into the running container unless you explicitly pass it into an `ENV`.

```dockerfile
FROM ubuntu
ARG VERSION=1.0
RUN echo "Building version $VERSION"
```

Pass a value at build time:
```
docker build --build-arg VERSION=2.5 -t myapp .
```

**ARG vs ENV — the key difference:**

```
+----------------------------+       +----------------------------+
|          ARG               |       |          ENV                |
|----------------------------|       |----------------------------|
| Available only during      |       | Available during build AND  |
| `docker build`             |       | at container runtime        |
|                            |       |                              |
| Set via --build-arg        |       | Set via ENV in Dockerfile or |
|                            |       | -e flag at `docker run`     |
|                            |       |                              |
| Gone once image is built   |       | Baked into the image, visible|
| (unless copied to ENV)     |       | with `docker inspect`/printenv|
+----------------------------+       +----------------------------+
```

Bridging ARG into ENV (common pattern — e.g. for app version tagging):

```dockerfile
FROM ubuntu
ARG VERSION=1.0
ENV APP_VERSION=$VERSION
CMD ["sh", "-c", "echo App version: $APP_VERSION"]
```

Now `$VERSION` (build-time) is captured into `$APP_VERSION` (persists at runtime).

## 6. Dockerfile `LABEL`

Attaches **metadata** (key-value pairs) to an image — not used by the running app, but useful for documentation, automation, and image management (CI/CD pipelines, registries, cleanup scripts).

```dockerfile
FROM ubuntu
LABEL maintainer="ram@example.com"
LABEL version="1.0"
LABEL description="Sample app image for study notes"
```

Or combined on one line:
```dockerfile
LABEL maintainer="ram@example.com" version="1.0" description="Sample app image"
```

Inspect labels on an image:
```
docker inspect myimage --format='{{json .Config.Labels}}'
```

Example use case: filter/find images by label
```
docker images --filter "label=maintainer=ram@example.com"
```

---

## Comparison Table: ENV vs ARG vs LABEL

| Feature | ENV | ARG | LABEL |
|---|---|---|---|
| Available at build time | Yes | Yes | No (metadata only) |
| Available at container runtime | Yes | No (unless passed to ENV) | No |
| Can be overridden at `docker run` | Yes (`-e`) | N/A (build only) | No |
| Can be overridden at `docker build` | No | Yes (`--build-arg`) | No |
| Purpose | App configuration | Build-time parameterization | Metadata/documentation |
| Visible via `docker inspect` | Yes | No | Yes |

## Key Takeaways

- `docker login` authenticates the CLI against a registry; required before pushing to (or pulling private images from) that registry.
- `docker tag` never duplicates an image — it just adds another name/reference to the same image ID. Required to match `<registry>/<username>/<repo>:<tag>` naming before push.
- `docker push` sends a tagged image to the registry; the standard order is **build → tag → login → push**.
- `ENV` variables persist into the running container and can be overridden at runtime with `-e`.
- `ARG` variables exist only during the image build and vanish afterward unless explicitly copied into an `ENV`.
- `LABEL` adds descriptive metadata to an image for organization/automation — it has zero effect on runtime behavior.

## Command Cheat Sheet

```bash
# Login / Logout
docker login
docker login myregistry.example.com
docker logout

# Tag
docker tag <local_image>:<tag> <registry>/<user>/<repo>:<tag>

# Push
docker push <registry>/<user>/<repo>:<tag>
docker push <registry>/<user>/<repo> --all-tags

# Build with ARG
docker build --build-arg VERSION=2.5 -t myapp .

# Run with ENV override
docker run -e APP_ENV=staging myimage

# Inspect env vars / labels
docker exec -it <container> printenv
docker inspect <image> --format='{{json .Config.Labels}}'

# Filter images by label
docker images --filter "label=maintainer=ram@example.com"
```
