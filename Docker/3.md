## Topic: Running Containers, Port Forwarding & Container Lifecycle

## 1. What Does It Take to Run a Container?

To run a container, you only need two things:

1. **Docker installed on a system** — this system is called the **Docker host**
2. **A Docker image** — the blueprint the container is built from

That's it. Once both are present, Docker can create and run a container from that image.

---

## 2. Port Forwarding — Letting the Outside World Reach Your Container

Most containers run **server-side applications** (like a web server) that need to be reached over the network. But a container's network is isolated from the host by default — so Docker needs a way to "forward" traffic from the host into the container. This is called **port forwarding** (or **port mapping**).

There are two ways to do this:

### A. Static Port Forwarding
You explicitly choose which host port maps to which container port.

```bash
docker container run -d --name web1 -p 8088:80 nginx
```

**What this means:**

| Part | Meaning |
|---|---|
| `-d` | Run in detached mode (in the background) |
| `--name web1` | Name the container `web1` |
| `-p 8088:80` | Map host port **8088** → container port **80** |
| `nginx` | Image to use |

➡️ Now, visiting `http://<host-ip>:8088` reaches Nginx running on port 80 *inside* the container.

### B. Dynamic Port Forwarding
Instead of picking the host port yourself, let Docker choose an available one automatically.

```bash
docker container run -d --name web3 -P nginx
```

**What this means:**

| Part | Meaning |
|---|---|
| `-P` (capital) | Publish all exposed container ports to **random** available host ports |

➡️ Use `docker port web3` afterward to find out which host port Docker picked.

> **Tip:** Use `-p` (lowercase) when you need a predictable, fixed port. Use `-P` (uppercase) when you don't care which port is used, as long as it works.

## 3. What Happens Behind the Scenes When a Container Is Created

Example command:

```bash
docker container run -d --name web4 -P httpd
```

Docker follows this sequence:

```
1. Check local storage
       │
       ▼
   Is "httpd:latest" already downloaded?
       │
   ┌───┴───┐
  YES       NO
   │         │
   │         ▼
   │   Connect to a registry (default = Docker Hub)
   │         │
   │         ▼
   │   Pull the image
   │         │
   └────┬────┘
        ▼
  Create the container from the image
```

**Key takeaway:** Docker always checks locally *first*. It only reaches out to Docker Hub (or another configured registry) if the image isn't already on your machine — this is why the first `run` of a new image is slower than subsequent ones.

## 4. Handy Bulk Cleanup Commands

| Goal | Command | How it works |
|---|---|---|
| Delete **all containers** | `docker rm -f $(docker ps -a -q)` | `docker ps -a -q` lists IDs of *all* containers (running + stopped); `-f` force-removes each one |
| Delete **all images** | `docker rmi $(docker images -q)` | `docker images -q` lists all image IDs, which are then removed |

> ⚠️ **Use with caution** — these commands are destructive and remove everything, not selectively.

## 5. What's Actually Running Inside a Container?

- Every container is built to run **one primary process/command** when it starts.
- This process runs as **PID 1** inside the container.
- The container stays **alive only as long as that PID 1 process keeps running.**
- Once that process exits, the container stops — even if other background processes are still around.

**Rule of thumb:** Your container's starting command should:
- Start the application, **and**
- Keep running continuously (not exit immediately)

This is why, for example, an Nginx image's default command runs Nginx in the foreground rather than as a background daemon — if it went to the background, PID 1 would exit and the container would immediately stop.

## 6. Container Lifecycle States

A container moves through distinct states:

```
   [Image]
      │
   docker create
      ▼
   Created ──────────────┐
      │                  │
   docker start          │
      ▼                  │
   Running                │
      │                  │
   docker stop            │
      ▼                  │
   Stopped ◄──────────────┘
      │
   docker rm
      ▼
   Removed (gone)
```

| State | Meaning |
|---|---|
| **Created** | Container exists but hasn't started running yet |
| **Running** | The PID 1 process is actively executing |
| **Stopped** | The process ended (or was stopped); container still exists on disk |
| **Removed** | Container is deleted entirely |

### Key relationship:
```
docker run  =  docker create  +  docker start
```
`docker run` is a convenience command that does both steps in one shot.

---

## 7. Removing Containers

You can't remove a running container directly — it must be stopped first, or you must force it.

```bash
# Proper way: stop, then delete
docker stop nginx1
docker rm nginx1

# Shortcut: force delete (stops + removes in one step)
docker rm -f nginx2
```

| Command | Behavior |
|---|---|
| `docker stop <name>` | Gracefully stops the running process |
| `docker rm <name>` | Deletes a **stopped** container |
| `docker rm -f <name>` | Force-stops (if running) and deletes immediately |

## Summary Cheat Sheet

```bash
# Static port mapping
docker container run -d --name web1 -p 8088:80 nginx

# Dynamic port mapping (random host port)
docker container run -d --name web3 -P nginx

# See which port was assigned dynamically
docker port web3

# Remove all containers
docker rm -f $(docker ps -a -q)

# Remove all images
docker rmi $(docker images -q)

# Stop then remove
docker stop nginx1 && docker rm nginx1

# Force remove (running or stopped)
docker rm -f nginx2
```
