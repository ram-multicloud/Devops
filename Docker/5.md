## Write the Dockerfile

```dockerfile
FROM nginx:1.29
COPY . /usr/share/nginx/html/
EXPOSE 80/tcp
```

### Build the image

```bash
docker build -t infinite_image:v1.0 .
```

### Run a container from the built image

```bash
docker run --name web1 -d -P infinite_image:v1.0
docker ps
```

### Tag the image with an alias (e.g., for Docker Hub)

```bash
docker image tag infinite_image:v1.0 shaikkhajaibrahim/infinite_image:v1.0
```

> An image can have **multiple tags/aliases** pointing to the same underlying image ID — useful for pushing to a registry under your username.

### Push the image to Docker Hub

Typical flow: sign up on Docker Hub → `docker login` → `docker push <username>/<image>:<tag>`.

## Manual vs. Dockerfile — Side-by-Side Cheat Sheet

| Step | Manual (Option 1) | Dockerfile (Option 2) |
|---|---|---|
| Start container | `docker run -d --name X -P nginx` | N/A — build defines it via `FROM` |
| Add website files | `docker cp . container:/usr/share/nginx/html` | `COPY . /usr/share/nginx/html/` |
| Save as image | `docker commit container new_image` | `docker build -t new_image .` |
| Repeatable? | ❌ No — manual steps every time | ✔ Yes — same Dockerfile, same result |
| Port declaration | Implicit via `-P` at run time | `EXPOSE` documents it in the image itself |
| Best for | Quick one-offs, learning | Production, CI/CD, version control |

---

## Key Takeaways

- `docker cp` moves files between host and a running container; `docker commit` freezes that container's state into a reusable image.
- The manual approach doesn't scale — every content change means redoing all steps by hand.
- A **Dockerfile** solves this: `FROM` (base + tag), `COPY` (add files), `EXPOSE` (document port) → `docker build` produces the same image every time.
- Images can carry **multiple tags** (e.g., a local tag and a Docker-Hub-ready `username/image:tag` alias) without duplicating the underlying data.
- `Already Exists` during a pull just means that image layer is already cached locally.
