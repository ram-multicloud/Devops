## Topic: Shell Form vs Exec Form (Docker `RUN`, `CMD`, `ENTRYPOINT`)

| Form | Syntax Style | What Actually Runs |
|---|---|---|
| **Shell form** | `RUN apt update` | `/bin/sh -c "apt update"` |
| **Exec form** | `CMD ["python", "test.py"]` | `python test.py` (direct exec, no shell) |

**Analogy:** Shell form is like asking a translator (`/bin/sh`) to relay your instruction to the process — the translator can interpret variables, chaining (`&&`, `|`), etc. Exec form is like speaking directly to the process yourself — faster, more literal, but no interpreter to expand anything for you.

## 2. Shell Form

- Internally wraps your command as: `/bin/sh -c <command>`
- Because a real shell is involved, you get shell features: environment variable expansion, pipes, chaining.

```dockerfile
RUN apt update
# runs as: /bin/sh -c apt update

RUN python test.py
# runs as: /bin/sh -c "python test.py"
```

## 3. Exec Form

- Starts the executable **directly**, bypassing the shell entirely.

```dockerfile
CMD ["python", "test.py"]
# runs as: python test.py   (no /bin/sh involved)
```

## 4. The Variable Expansion Gotcha

This is the part students most often get wrong.

```dockerfile
CMD ["wget", "$URL"]     # ❌ Does NOT work — no shell to expand $URL
RUN  wget ${URL}         # ✅ Works — shell form expands the variable
```

**Why:** Exec form passes arguments to the executable as a literal array — there's no shell present to substitute `$URL` with its value. Shell form runs through `/bin/sh`, which *does* perform that substitution before executing.

**Rule of thumb:** If you need dynamic values (build args, environment variables, shell expansion), you must use **shell form**.

## 5. Signal Handling — Why It Matters

| Form | Signal Handling |
|---|---|
| **Exec form** | ✅ Respects Linux signals directly — Docker can send `SIGTERM`/`SIGKILL` straight to your process (PID 1) |
| **Shell form** | ⚠️ Signals go to the shell process first, and may not propagate cleanly to your actual application |

This matters specifically for `CMD` and `ENTRYPOINT`, because these define the **container's main process** — the one Docker signals when you run `docker stop` or `docker restart`.

- With **exec form**, your app receives the signal directly and can shut down gracefully.
- With **shell form**, `/bin/sh` is PID 1, and it may not forward the signal to your application — leading to a hard kill after the timeout instead of a graceful stop.
