# Two Ways to Create a Docker Image

## Overview

Docker images can be created in **two ways**:

1. **Interactively** — manually configure a running container, then save it as an image
2. **Dockerfile (Instruction-based)** — define build steps in a file; Docker builds the image automatically

```
                 ┌──────────────────────────┐
                 │  Ways to Create an Image  │
                 └────────────┬─────────────┘
                              │
              ┌───────────────┴───────────────┐
              ▼                                ▼
   ┌───────────────────────┐        ┌────────────────────────────────┐
   │      Interactively    │        │  Instruction file (Dockerfile) │
   │  (manual, ad-hoc)     │        │   (scripted, repeatable)       │
   └───────────────────────┘        └────────────────────────────────┘
```

| Aspect | Interactive | Dockerfile |
|---|---|---|
| How it's built | Manual commands inside/on a container | Declared as steps in a text file |
| Repeatability | Low — steps must be redone manually | High — same result every build |
| Version control | Not possible (no script to track) | Yes — Dockerfile can be committed to Git |
| Automation (CI/CD) | Difficult | Easy (`docker build`) |
| Best for | Learning, quick experiments | Real projects, production images |

---

## Method 1: Interactively

**Idea:** Start a container, configure it by hand (install software, copy files, etc.), then freeze its current state into a new image using `docker commit`.

### Example — Dockerizing a Website

**Step 1: Run a base nginx container**
```bash
docker run -d --name web1 -p 80:80 nginx
```

**Step 2: Get a website template (on the host)**
```bash
mkdir website && cd website/
wget https://templatemo.com/tm-zip-files-2020/templatemo_623_novapay.zip
unzip templatemo_623_novapay.zip
cd templatemo_623_novapay/
```

**Step 3: Copy files from host into the running container**
```bash
docker cp . web1:/usr/share/nginx/html/
```

**Step 4: Verify** — browse to the server's IP; the custom site loads.

**Step 5: Save the container as a new image**
```bash
docker commit web1 novapay
docker image ls
```

**Step 6: Test the new image**
```bash
docker rm -f web1
docker run -d --name web2 -p 80:80 novapay
```

`web2` serves the website immediately — no manual copying needed, since it's already baked into the `novapay` image.

**Step 7: Clean up**
```bash
docker rm -f web2
```

### Limitations of the Interactive Method
- ❌ Manual and repetitive — every image needs the same steps redone
- ❌ Error-prone — easy to miss a step
- ❌ No record of *how* the image was built
- ❌ Hard to plug into automated pipelines

## Method 2: Instruction File (Dockerfile)

**Idea:** Write the build steps once in a file called `Dockerfile`. Docker reads it and builds the image automatically — same result, every time.

### Common Dockerfile Instructions

| Instruction | Purpose |
|---|---|
| `FROM` | Base image to start from |
| `WORKDIR` | Sets the working directory inside the image |
| `COPY` / `ADD` | Copies files from host into the image |
| `RUN` | Executes a command during the build (e.g., install packages) |
| `EXPOSE` | Documents which port the container listens on |
| `CMD` / `ENTRYPOINT` | Command to run when the container starts |

### Example — Same Website, Built via Dockerfile

**Folder structure:**
```
novapay-app/
├── Dockerfile
└── templatemo_623_novapay/   (extracted website files)
```

**Dockerfile:**
```dockerfile
# 1. Start from the official nginx image
FROM nginx

# 2. Copy website files into nginx's default web root
COPY templatemo_623_novapay/ /usr/share/nginx/html/

# 3. Document the port nginx listens on
EXPOSE 80

# 4. Default command (nginx image already runs this, shown here for clarity)
CMD ["nginx", "-g", "daemon off;"]
```

**Build the image:**
```bash
docker build -t novapay:v1 .
```

**Run a container from it:**
```bash
docker run -d --name web3 -p 80:80 novapay:v1
```

That's it — one command (`docker build`) reproduces the exact same image every time, on any machine, without manual copying or committing.

### Example — A Simple Node.js App (Second Dockerfile Example)

```dockerfile
FROM node:18

WORKDIR /app

COPY package.json .
RUN npm install

COPY . .

EXPOSE 3000

CMD ["node", "app.js"]
```

```bash
docker build -t my-node-app:1.0 .
docker run -d --name node1 -p 3000:3000 my-node-app:1.0
```

### Advantages of the Dockerfile Method
- ✅ Fully repeatable and automatable
- ✅ Version-controlled — the Dockerfile itself documents the build
- ✅ Easy to share with a team or plug into CI/CD
- ✅ No manual `docker cp` / `docker commit` steps needed

---

## Side-by-Side Comparison

| Step | Interactive | Dockerfile |
|---|---|---|
| Start point | `docker run` a base image | `FROM` in Dockerfile |
| Add files | `docker cp` into running container | `COPY`/`ADD` instruction |
| Install software | Run commands manually inside container (`docker exec`) | `RUN` instruction |
| Save result | `docker commit container_name image_name` | `docker build -t image_name .` |
| Reproducibility | One-time, manual | Every build is identical |

---

## Key Takeaways

- Both methods produce a Docker **image** — the difference is *how* they get there.
- **Interactive** = fast to try, but not repeatable or trackable.
- **Dockerfile** = the standard, production-grade approach — declarative, versioned, and automatable.
- `docker commit` ↔ `docker build` are the two "save the image" commands for each respective method.
