## Big picture

**three generations of infrastructure:**

| Generation | Isolation | OS overhead | Startup time | Hardware efficiency |
|---|---|---|---|---|
| Physical server | Whole machine | Full OS per app | Minutes (manual setup) | Poor — one app per box |
| Hypervisor / VMs | Virtual machine | Full guest OS per VM | Minutes | Good — many VMs per box |
| Containers | Process-level | Shares host kernel | Seconds | Best — many containers per box |

## Example scenario: deploying a website

### Option 1 — physical server

**What you do**
1. Rack and power on a physical server
2. Install the operating system
3. Install a web server (e.g. Apache/Nginx)
4. Copy the website's HTML and other files onto it

**Limitation:** one machine is dedicated to one workload. If the app only needs 10% of the server's capacity, the other 90% sits idle. Scaling means buying another physical machine.

### Option 2 — hypervisor (e.g. VMware)

**What you do**
1. Install a hypervisor on the physical server
2. The hypervisor creates virtualized hardware (virtual CPU, RAM, disk, network)
3. Use those virtual resources to spin up multiple virtual machines (VMs)
4. Each VM runs its own full guest OS, with its own app installed on top

**Improvement:** one physical server now hosts many isolated workloads instead of one, so hardware is used far more efficiently.

**Limitation:** every VM still needs a complete guest operating system — duplicated OS overhead, slower boot times, and a larger disk/memory footprint per workload.

### Option 3 — containers

**What you do**
1. Run a container engine (like Docker) on the host OS
2. Each container gets an isolated slice of CPU, RAM, a minimal OS layer, disk, and network — but shares the host machine's kernel instead of running a full guest OS
3. The application itself gets top priority: almost all resources go to running the app, not to OS overhead

**Improvement:** containers start in seconds (not minutes), use far less disk/memory than a VM, and let you pack many more isolated workloads onto the same hardware.

## The story of Docker

| Step | What happened |
|---|---|
| 1 | A startup called **dotcloud** set out to build a Platform-as-a-Service (PaaS) |
| 2 | While building it, the team created an internal tool to make containers easier to create and manage — this tool became **Docker** |
| 3 | Docker was open-sourced; co-founder **Solomon Hykes** demoed it at PyCon and it was an overnight success |
| 4 | On the back of that success, the company itself was renamed **Docker Inc.** |

## Key takeaway

Containers won out over VMs for the same reason Docker won out as the tool of choice: less overhead, faster startup, and the ability to run far more isolated workloads on the same hardware — exactly what modern DevOps and cloud-native deployments are built around.
