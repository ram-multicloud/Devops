# Docker: Arguments, Labels, and Networking

## 1. Docker Build Arguments (`ARG`)

`ARG` defines build-time variables — values available **only during the image build process**. They are not available in the running container unless explicitly passed into an `ENV`.

### Syntax (Dockerfile)

```dockerfile
ARG VARIABLE_NAME=default_value
```

### Example

**Dockerfile**
```dockerfile
FROM ubuntu:22.04

ARG APP_VERSION=1.0
ARG BUILD_ENV=production

RUN echo "Building version $APP_VERSION for $BUILD_ENV"

# ARG values are NOT available at runtime unless copied to ENV
ENV APP_VERSION=$APP_VERSION
```

**Build with a custom value:**
```bash
docker build --build-arg APP_VERSION=2.5 --build-arg BUILD_ENV=staging -t myapp:2.5 .
```

**Key points:**
- `ARG` values exist only during the build (inside the Dockerfile).
- They can have a default value, which is overridden by `--build-arg`.
- Scope: an `ARG` declared before `FROM` is only available to that `FROM` line (used for multi-stage base image selection). An `ARG` declared after `FROM` is available to that stage only.
- To use an `ARG` at runtime, copy it into `ENV`.

### `ARG` vs `ENV`

| Feature | `ARG` | `ENV` |
|---|---|---|
| Available at build time | Yes | Yes |
| Available at runtime (container) | No | Yes |
| Set via | `--build-arg` | Dockerfile `ENV` or `docker run -e` |
| Persisted in final image | No | Yes |

### Runtime container arguments (CMD/ENTRYPOINT args)

Separate from build `ARG`, you can also pass arguments to a running container's entrypoint command:

```bash
docker run myimage --port=8080 --debug
```

These are passed as `CMD` arguments and picked up by `ENTRYPOINT`:

```dockerfile
ENTRYPOINT ["python3", "app.py"]
CMD ["--port=5000"]
```

Running `docker run myimage --port=8080` overrides the default `CMD` value, so the container executes `python3 app.py --port=8080`.

## 2. Docker Labels

Labels are **key-value metadata** attached to Docker objects (images, containers, volumes, networks). They're used for organization, filtering, automation, and documentation — they have no effect on runtime behavior.

### Adding labels in a Dockerfile

```dockerfile
FROM nginx:latest

LABEL maintainer="ram@example.com"
LABEL version="1.0"
LABEL description="Web server for production frontend"
LABEL team="devops"
```

Multiple labels can also be combined in one line:

```dockerfile
LABEL maintainer="ram@example.com" \
      version="1.0" \
      environment="production"
```

### Adding labels at runtime (`docker run`)

```bash
docker run -d \
  --name web1 \
  --label environment=production \
  --label owner=ram \
  nginx
```

### Viewing labels

```bash
docker inspect --format '{{json .Config.Labels}}' web1
```

### Filtering by label

```bash
docker ps --filter "label=environment=production"
docker images --filter "label=team=devops"
```

**Common uses:**
- CI/CD pipelines tagging build metadata (commit hash, build number).
- Organizing containers by team, environment, or project.
- Automation tools (like Traefik or Watchtower) reading labels to configure routing or update policies.

## 3. Docker Networking

Docker networking controls how containers communicate with each other, the host, and the outside world. Docker provides several network drivers.

### Network drivers overview

| Driver | Use case |
|---|---|
| `bridge` | Default; containers on the same host communicate via a private internal network |
| `host` | Container shares the host's network stack directly (no isolation) |
| `none` | Container has no networking |
| `overlay` | Multi-host networking, used in Docker Swarm |
| `macvlan` | Assigns a container a MAC address, making it appear as a physical device on the network |

### Listing networks

```bash
docker network ls
```

### Bridge network (default)

Every container connects to the default `bridge` network unless specified otherwise.

```bash
docker run -d --name container1 nginx
docker run -d --name container2 nginx
```

Containers on the **default** bridge network cannot resolve each other by container name (only by IP). To get name-based DNS resolution, create a **user-defined bridge network**:

```bash
docker network create mynetwork

docker run -d --name web --network mynetwork nginx
docker run -d --name db --network mynetwork mysql
```

Now `web` can reach `db` simply using the hostname `db`:

```bash
# from inside the web container
ping db
```

### Host network

The container uses the host machine's network directly — no port mapping needed, but no isolation either.

```bash
docker run -d --network host nginx
```

### None network

Completely disables networking for the container.

```bash
docker run -d --network none myisolatedapp
```

### Inspecting a network

```bash
docker network inspect mynetwork
```

Shows connected containers, subnet, gateway, and driver details.

### Connecting/disconnecting a running container

```bash
docker network connect mynetwork container1
docker network disconnect mynetwork container1
```

### Example: Multi-container app on a custom network

```bash
# Create a dedicated network
docker network create appnet

# Run a database container
docker run -d --name db --network appnet -e MYSQL_ROOT_PASSWORD=pass mysql:8

# Run an app container that connects to db by name
docker run -d --name app --network appnet -p 8080:80 myapp:latest
```

Inside `app`, the database is reachable at `db:3306` — no IP addresses needed, thanks to Docker's embedded DNS on user-defined networks.

### Removing a network

```bash
docker network rm mynetwork
```
