# Docker: Image Layers, Volumes, and Multi-Stage Builds

---

## 1. Docker Image Layers

### What is a layer?

Every instruction in a Dockerfile (`FROM`, `RUN`, `COPY`, `ADD`, etc.) creates a new **read-only layer**. Docker stacks these layers on top of each other using a **union filesystem (UnionFS/OverlayFS)** to produce the final image.

```
┌─────────────────────────────┐
│  Layer 5: CMD ["node","app"]│  ← metadata only, no filesystem change
├─────────────────────────────┤
│  Layer 4: COPY . .          │
├─────────────────────────────┤
│  Layer 3: RUN npm install   │
├─────────────────────────────┤
│  Layer 2: COPY package.json │
├─────────────────────────────┤
│  Layer 1: FROM node:20      │  ← base image (itself made of layers)
└─────────────────────────────┘
```

Think of it like a **transparent sheet stack** — each sheet (layer) only records what changed, but looking through all of them together gives you the complete picture (the final filesystem).

### Key properties

| Property | Explanation |
|---|---|
| **Immutable** | Once built, a layer never changes. A new instruction always creates a *new* layer. |
| **Cached** | Docker reuses a layer from cache if the instruction and its inputs are unchanged. |
| **Shared** | Multiple images can share the same base layers, saving disk space. |
| **Ordered** | Layers are applied in Dockerfile order — this order affects caching efficiency. |
| **Read-only** | Image layers are read-only. Only the top **container layer** (added at `docker run`) is writable. |

### The writable container layer

When you run a container, Docker adds one thin **read-write layer** on top of the image's read-only layers. Any file changes during the container's life happen here.

```
┌────────────────────────────┐
│ Container layer (R/W)      │  ← created at `docker run`, deleted with the container
├────────────────────────────┤
│ Image layers (Read-Only)   │  ← shared across all containers from this image
└────────────────────────────┘
```

This is why container data is **ephemeral by default** — delete the container, and the writable layer (and anything written to it) is gone. This is the exact problem **volumes** solve (see Section 2).

### Layer caching and build performance

Docker builds top-down and **invalidates the cache from the first changed instruction onward** — every layer after it is rebuilt, even if unchanged.

**Bad ordering (cache-unfriendly):**
```dockerfile
FROM node:20
COPY . .                 # any file change invalidates this AND everything below
RUN npm install
CMD ["node", "app.js"]
```

**Good ordering (cache-friendly):**
```dockerfile
FROM node:20
COPY package.json .
RUN npm install           # cached unless package.json changes
COPY . .                  # only this layer rebuilds on code changes
CMD ["node", "app.js"]
```

**Rule of thumb:** put things that change **least often** (base image, dependency manifests) near the top, and things that change **most often** (application source code) near the bottom.

### Inspecting layers

```bash
docker history <image>        # list layers, size, and the command that created each
docker inspect <image>        # full metadata including layer digests
```

## 2. Docker Volumes

### The problem volumes solve

Container filesystems are tied to the container's writable layer. When a container is removed, that data disappears. **Volumes** decouple data from the container lifecycle so it survives restarts, removals, and even container replacement.

### Types of data persistence in Docker

| Type | Managed by | Location | Typical use |
|---|---|---|---|
| **Named volume** | Docker | `/var/lib/docker/volumes/...` | Databases, app data — Docker-managed, portable |
| **Bind mount** | You (the host) | Any host path you choose | Local development, sharing config/source code |
| **tmpfs mount** | Docker (in-memory) | RAM only, never written to disk | Secrets, temp/cache data |
| **Anonymous volume** | Docker | Auto-generated path | Auto-created, hard to reference later — avoid for real data |

```
                HOST MACHINE
   ┌─────────────────────────────────────┐
   │                                     │
   │  /var/lib/docker/volumes/mydata ────┼──┐
   │  (named volume, Docker-managed)     │  │
   │                                     │  │
   │  /home/user/project ────────────────┼──┤   mounted into
   │  (bind mount, host path)            │  │   container's
   │                                     │  │   filesystem
   │  RAM (tmpfs) ───────────────────────┼──┤
   │                                     │  │
   └─────────────────────────────────────┘  │
                                             ▼
                                  ┌────────────────────┐
                                  │     CONTAINER      │
                                  │  /app/data  <──────┼── named volume
                                  │  /app/src   <──────┼── bind mount
                                  │  /tmp/cache <──────┼── tmpfs
                                  └────────────────────┘
```

### Named volumes

Docker creates and manages the storage location for you.

```bash
docker volume create mydata
docker run -d -v mydata:/var/lib/mysql mysql:8

# Equivalent, more explicit syntax
docker run -d --mount source=mydata,target=/var/lib/mysql mysql:8
```

- Survives `docker rm` of the container.
- Reusable across multiple containers.
- Best for production data (databases, message queues) since Docker manages permissions and location.

### Bind mounts

You mount an exact path from the host into the container.

```bash
docker run -v /home/user/myapp:/app node:20
docker run --mount type=bind,source=/home/user/myapp,target=/app node:20
```

- Full control over the host path — great for live-editing source code during development (hot reload).
- Tightly coupled to the host's directory structure — less portable across machines.
- Container can read/write directly to host files, so permission mismatches (UID/GID) are a common gotcha.

### tmpfs mounts (Linux only)

Data lives only in memory — never touches disk.

```bash
docker run --tmpfs /app/cache node:20
```

- Fast, and automatically wiped when the container stops.
- Good for secrets or sensitive temp data you don't want persisted to disk at all.

### `-v` vs `--mount`: quick comparison

| | `-v` / `--volume` | `--mount` |
|---|---|---|
| Syntax | Compact, colon-separated | Verbose, key=value |
| Creates host path if missing | Yes (silently) | No — errors if source doesn't exist (for bind mounts) |
| Recommended for | Quick local use | Production / scripts (explicit, less error-prone) |

### Common volume commands

```bash
docker volume ls                    # list all volumes
docker volume inspect mydata        # details: mountpoint, driver, labels
docker volume rm mydata             # remove a volume
docker volume prune                 # remove all unused volumes
```

### Volumes in Docker Compose

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data   # named volume
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql   # bind mount

volumes:
  pgdata:   # declares the named volume
```

## 3. Multi-Stage Builds

### The problem

A single-stage Dockerfile often ends up carrying build tools, compilers, and source code into the **final image** — things needed only to *build* the app, not to *run* it. That means bloated, slower, less secure images.

```dockerfile
# Single-stage: everything ends up in the final image
FROM node:20
WORKDIR /app
COPY . .
RUN npm install && npm run build     # dev deps + build tools stay in the image!
CMD ["node", "dist/server.js"]
```

### The solution: multiple `FROM` stages

A multi-stage build uses **more than one `FROM`** in a single Dockerfile. Each `FROM` starts a fresh, independent stage. You build/compile in an early stage, then **copy only the finished artifacts** into a clean, minimal final stage — leaving the build tools behind.

```
┌────────────────────────┐        ┌────────────────────────┐
│   STAGE 1: "builder"   │        │   STAGE 2: final image │
│   FROM node:20         │        │   FROM node:20-alpine  │
│                        │        │                        │
│   - npm install        │        │   - only runtime deps  │
│   - npm run build      │──────▶ │   - COPY --from=builder│
│   - full dev toolchain │  copy  │     the compiled output│
│   - source code        │ artifact│                       │
│ (discarded after-build)│        │  (this is what ships)  │
└────────────────────────┘        └────────────────────────┘
```

### Example: Node.js app

```dockerfile
# ---- Stage 1: build ----
FROM node:20 AS builder
WORKDIR /app
COPY package*.json .
RUN npm install
COPY . .
RUN npm run build          # produces /app/dist

# ---- Stage 2: run ----
FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
CMD ["node", "dist/server.js"]
```

- `AS builder` names the first stage so it can be referenced later.
- `COPY --from=builder <path> <path>` pulls only the compiled output — no source code, no dev dependencies, no build tools — into the final image.

### Example: Go app (extreme size reduction)

Go's static binaries make this pattern especially powerful:

```dockerfile
# ---- Stage 1: build ----
FROM golang:1.22 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app

# ---- Stage 2: run ----
FROM scratch
COPY --from=builder /app /app
ENTRYPOINT ["/app"]
```

`FROM scratch` means literally nothing — not even a shell or libc. The final image contains **only the compiled binary**. This can shrink an image from ~800 MB (with the full Go toolchain) down to a few MB.

### Referencing external images as a stage

You can also copy from a stage in a *different* image, not just one you built:

```dockerfile
COPY --from=nginx:latest /etc/nginx/nginx.conf /tmp/nginx.conf
```

### Building a specific stage only

Useful for debugging — build and run just the `builder` stage without needing the final one:

```bash
docker build --target builder -t myapp:builder .
```

### Why multi-stage builds matter

| Benefit | Explanation |
|---|---|
| **Smaller final images** | Build tools, compilers, and source code never reach the shipped image. |
| **Better security** | Fewer packages in the final image = smaller attack surface, no leaked build secrets/toolchains. |
| **Cleaner Dockerfiles** | No need for separate build scripts or two Dockerfiles (`Dockerfile.build` + `Dockerfile.prod`). |
| **Still cache-friendly** | Each stage caches independently — changing final-stage instructions doesn't invalidate the builder stage. |

### How the three concepts connect

- **Layers** are the mechanism every stage is built from — each stage still creates its own layer stack.
- **Multi-stage builds** control which layers make it into the *final* image, discarding the build-only stages entirely.
- **Volumes** are unrelated to build-time size — they matter at *runtime*, for persisting data the running container writes (which multi-stage builds don't affect, since volumes attach to containers, not images).
